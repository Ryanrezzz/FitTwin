# Deploying FitTwin to Render

Two services from this repo (`render.yaml`), plus MongoDB Atlas. ~20 minutes.

Render has **no managed MongoDB**, so the database lives at Atlas. Everything
else is covered by the blueprint.

---

## 1 · Database — MongoDB Atlas (free)

1. [cloud.mongodb.com](https://cloud.mongodb.com) → create a free **M0** cluster.
2. **Database Access** → add a user; save the password.
3. **Network Access** → add `0.0.0.0/0`. Render's free tier has no static
   egress IP, so an allow-list isn't possible — which is exactly why the DB user
   needs a strong, unique password.
4. Copy the connection string:
   `mongodb+srv://USER:PASSWORD@cluster0.xxxx.mongodb.net/?retryWrites=true&w=majority`

Indexes are created automatically on first boot by Beanie — no migration step.

---

## 2 · Deploy the blueprint

Push this repo to GitHub, then in Render: **New → Blueprint** → pick the repo.
It reads `render.yaml` and creates `fittwin-api` and `fittwin-web`.

Set the `sync: false` variables on **fittwin-api** when prompted:

| Variable | Value |
|---|---|
| `MONGO_URI` | the Atlas string from step 1 |
| `OPENAI_API_KEY` | your key |
| `GOOGLE_CLIENT_ID` | `…apps.googleusercontent.com` (optional; blank disables the button) |
| `CORS_ORIGINS` | leave blank for now — step 3 |

`JWT_SECRET` is generated by Render automatically. **Never replace it by hand:**
changing it invalidates every existing session.

---

## 3 · Wire the two URLs together

Neither URL exists until the first deploy, so this is a second pass.

1. Copy each service's URL, e.g.
   `https://fittwin-api.onrender.com` and `https://fittwin-web.onrender.com`.
2. On **fittwin-api**: set `CORS_ORIGINS` to the **web** URL.
3. On **fittwin-web**: set `VITE_API_BASE_URL` to the **api** URL, then
   **Manual Deploy → Clear build cache & deploy**.

> ⚠️ **Vite inlines env vars at build time.** Setting `VITE_API_BASE_URL` without
> rebuilding does nothing — the old value is already baked into the JS bundle.
> This is the single most common failure here.

4. Google sign-in: add the **web** URL to your OAuth client's
   *Authorised JavaScript origins* (alongside `http://localhost:5173`).
   Allow a few minutes for propagation.

---

## 4 · Verify

```bash
curl https://fittwin-api.onrender.com/health                 # {"status":"ok"}
curl https://fittwin-api.onrender.com/api/v1/health/ready    # graph compiled
```

Then open the web URL, register, onboard, and generate a plan. If the plan
appears but the coach's language is generic, the LLM silently fell back — see
Troubleshooting.

## Troubleshooting

**API won't start, logs show `JWT_SECRET is unset, default, or too short`.**
Working as designed: `APP_ENV=production` refuses to boot with a forgeable
secret. Let Render generate `JWT_SECRET` rather than setting it manually.

**Every request fails CORS.** `CORS_ORIGINS` must be the web service's exact
origin — scheme + host, no trailing slash, no path.

**The frontend calls `localhost:8000` in production.** `VITE_API_BASE_URL` was
set but not rebuilt. Redeploy the static site.

**Refreshing `/coach` returns 404.** The SPA rewrite in `render.yaml` is missing
or was edited out.

**Plans generate but the writing is flat and identical every time.** The LLM
provider failed to initialise and the circuit breaker fell back to the offline
`fake` provider — by design, the app never errors on LLM failure. Check the API
logs for `Could not init provider`, and confirm `OPENAI_API_KEY` is set and the
SDK for your `LLM_PROVIDER` is in `requirements.txt`.

**Google button missing.** `GOOGLE_CLIENT_ID` is unset — the button hides itself
rather than failing on click. Set it and redeploy the API.

## Free-tier reality

A free Render web service **spins down after ~15 minutes idle**, and the next
request waits ~50 seconds while it cold-starts. With plan generation calling an
LLM on top, someone opening your link may assume it's broken.

Options: use the cheapest paid instance for the API, or add a "waking up…" state
to the SPA's first load. Static sites don't sleep, so the page appears instantly
and only the API stalls — which makes the missing loading state more noticeable,
not less.

## Before going public

- **Rotate the Gemini key** that was exposed in chat (HANDOFF §2.6).
- **Publish the OAuth consent screen** — in *Testing* only listed test users can
  sign in. `email`/`profile` scopes need no Google review.
- The rate limiter is **in-process**; it resets on restart and is per-instance.
  Fine for one instance, needs Redis if you scale out.
- There is still **no password reset** (HANDOFF §8.1).
